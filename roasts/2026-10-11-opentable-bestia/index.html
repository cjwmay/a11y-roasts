OpenTable 餐厅页：预订组件的图标按钮没有可见文字

OpenTable Restaurant Page: The Booking Widget's Icon Buttons Have No Visible Labels

原定审 Zillow 房源页，但 Zillow 对真机浏览器返回 "Access to this page has been denied"（bot 校验）—— 按流程不绕过，改用备选 OpenTable。审的是洛杉矶热门餐厅 Bestia 的页面（4.7 星，9,212 条评价）。方法：真机键盘走查 + accessibility tree 快照 + aria-label/alt/href 属性取证。以下为 2026-10-11 抓到的版本。

The plan was a Zillow listing page, but Zillow answered the real browser with "Access to this page has been denied" (bot protection) — per protocol, no bypass; I switched to the backup, OpenTable. The audited page is a popular LA restaurant, Bestia (4.7 stars, 9,212 reviews). Method: real-browser keyboard walkthrough + accessibility-tree snapshots + aria-label/alt/href forensics. This reflects the version captured on 2026-10-11.

①吸顶预订组件的图标 combobox，名字里没有可见文字Sticky booking widget's icon-only comboboxes have no visible text in their namesMedium

现象

右上角吸顶预订组件里，"2 people"（人数）和 "7:00 PM"（时间）两个选择器是图标 + combobox 组合，人形/时钟图标旁没有文字标签。取证：accessibility tree 里它们的名字是 "Party size selector" 和 "Time selector"，显示的值 "2 people" / "7:00 PM" 不在名字里。

用户影响

Voice Control 用户说"click 2 people"，系统按名字匹配控件 —— "Party size selector" 对不上，点不中。而这恰恰是全页最核心的转化组件。对照组：同一页 inline 预订变体渲染成单个按钮 "For 2 people, Oct 11, 2026, 7:00 PM"，名字含可见文字，是对的。

WCAG 依据

2.5.3 Label in Name（可见标签的文字必须出现在 accessible name 里）。同类：reviews 区排序 combobox 名字叫 "Sort by"、显示 "Newest"，但页面上根本看不到 "Sort by" 几个字。

修复方案

二选一或并用：① 给图标配可见文字标签（"Party size" / "Time"），让名字从可见文本计算；② 让 accessible name 包含当前值：aria-label="Party size, 2 people"，值变时同步更新。

What

In the sticky booking widget (top-right), the "2 people" (party size) and "7:00 PM" (time) selectors pair an icon with a combobox — no text labels next to the person/clock icons. Forensics: the accessibility tree names them "Party size selector" and "Time selector"; the visible values "2 people" / "7:00 PM" appear nowhere in the names.

Impact

Voice Control users saying "click 2 people" match controls by name — "Party size selector" won't match, and the tap can miss. And this is the page's single most important conversion widget. The positive control: the same page's inline booking variant renders one button named "For 2 people, Oct 11, 2026, 7:00 PM" — name contains the visible text, correct.

WCAG

2.5.3 Label in Name (visible label text must appear in the accessible name). Same family: the reviews sort combobox is named "Sort by" showing "Newest", but no "Sort by" text is visible on screen.

Fix

Either or both: ① give the icons visible text labels ("Party size" / "Time") so names compute from visible text; ② include the current value in the accessible name: aria-label="Party size, 2 people", updating as the value changes.

②三张不同的室内照片，按钮名字一字不差Three different interior photos share one identical button nameLow

现象

Photos 区三张室内照片缩略图，accessibility tree 里三个按钮全叫 "Enlarge image: Interior - Bestia, Los Angeles, CA"（dup=1/3、2/3、3/3）—— 三张不同的照片，名字完全无法区分。

用户影响

读屏用户听到三个"一样的按钮"，想回看"刚才那张吧台的照片"只能靠运气。和第 1 期 Airbnb 的"80 个没名字按钮"同家族：照片有描述数据（Hero 图 alt 就是 "Exterior - Bestia, Los Angeles, CA"），只是缩略图模板没把区分信息接进来。

WCAG 依据

1.1.1 Non-text Content（信息性图片需要有意义的替代文本）。

修复方案

模板里加序号："Enlarge photo 2 of 23: Interior - Bestia" —— 不需要新文案，序号即区分度；照片元数据若有拍摄位置（dining room / bar）可拼入。

What

Three interior-photo thumbnails in the Photos section are all named "Enlarge image: Interior - Bestia, Los Angeles, CA" in the accessibility tree (dup=1/3, 2/3, 3/3) — three different photos, indistinguishable by name.

Impact

Screen reader users hear three identical "buttons" and can only guess which opens the bar photo they just saw. Same family as Roast #1's "80 nameless buttons": descriptive data exists (the hero image's alt is "Exterior - Bestia, Los Angeles, CA"), the thumbnail template just doesn't wire differentiation in.

WCAG

1.1.1 Non-text Content (informative images need meaningful text alternatives).

Fix

Add position to the template: "Enlarge photo 2 of 23: Interior - Bestia" — no new copy needed, the index is the differentiation; stitch in a location (dining room / bar) if photo metadata carries it.

③面包屑里两个 "Downtown" 链接，名字一样、去向不同Two "Downtown" breadcrumb links, same name, different destinationsLow

现象

h1 下的面包屑 "Home > United States > Los Angeles > Downtown > Downtown" —— 两个 "Downtown" 名字完全相同，href 却指向不同页面：…/region/…/downtown-south-and-east-la-restaurants（大区）vs …/neighborhood/…/downtown-los-angeles-restaurants（街区）。

用户影响

读屏用户听到"Downtown、Downtown"，分不清哪个是大区、哪个是街区；连视觉用户都要靠位置猜。

WCAG 依据

2.4.4 Link Purpose (In Context) —— 链接目的应从名字或上下文可辨。

修复方案

把层级含义写进名字，如 "Downtown LA（大区）" / "Downtown（街区）"，或用 aria-label 区分。文案级修复，成本最低的一类。

What

The breadcrumb under the h1 reads "Home > United States > Los Angeles > Downtown > Downtown" — two "Downtown" links with identical names but different hrefs: …/region/…/downtown-south-and-east-la-restaurants (district) vs …/neighborhood/…/downtown-los-angeles-restaurants (neighborhood).

Impact

Screen reader users hear "Downtown, Downtown" with no way to tell district from neighborhood; even sighted users must guess from position.

WCAG

2.4.4 Link Purpose (In Context) — link purpose should be determinable from the name or its context.

Fix

Write the hierarchy into the name — "Downtown LA (district)" / "Downtown (neighborhood)" — or disambiguate with aria-label. Copy-level fix, cheapest kind there is.

  • Skip link "Skip to main content" is first in tab order and visible on focus (2.4.1); focus ring visible throughout, logical tab order, no keyboard traps (2.4.7 / 2.1.2).
  • Exactly one h1. Save/photos/map buttons all well-named (4.1.2). Photo gallery dialog opens with Enter, closes with Escape.
